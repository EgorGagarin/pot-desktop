# ADR 202611102037: Кэш переводов — SQLite (L1) + индекс + Map в памяти (L0)

- **Статус:** принято
- **Дата:** 2026-11-10 20:37 (UTC+5)
- **Связан с:** [ADR 202611101859](202611101859-adr-svelte-rewrite.md) (после его оптимизаций сеть осталась единственным доминирующим звеном)
- **Автор:** Egor Gagarin, проработка — ZCode-агент

---

## 1. Контекст

Повторный перевод той же фразы сейчас всегда идёт в сеть: эффект в
`TargetArea/index.jsx:96` при каждом новом тексте сразу вызывает `translate()` →
HTTP-запрос (~1,1 с для Yandex, ~секунды для qwen). Кэшей в проекте нет —
единственные «cache» в коде это HTTP-заголовки Bing и пути к скриншотам.

При этом локальная БД уже существует: SQLite `history.db` через tauri-plugin-sql,
таблица `history(id, text, source, target, service, result, timestamp)`,
заполняется после каждого успешного перевода (`TargetArea:127, addToHistory`,
если не включён `history_disable`). Читается только страницей «История»
(`History/index.jsx:49-62`) для просмотра. То есть **история — готовый,
наполовину используемый кэш**: она содержит всё нужное, но никогда не
запрашивается до сетевого вызова.

Типовой сценарий пользователя: перевод тех же слов и устойчивых выражений
повторно (чтение документации) — идеальный случай для кэша.

## 2. Рассмотренные варианты

### Вариант A (отклонён): Redb

Чисто быстрее нативно: точечный lookup ~0,5–2 мкс против ~1–10 мкс у SQLite
(по бенчмаркам автора redb — быстрее в ~1,5–3 раза на точечных операциях).
Но проверка кэша живёт в JS, а хранилище — в Rust-процессе, поэтому реальная
цена попадания = invoke IPC с JSON-сериализацией (~0,1–1 мс) + lookup
(наносекунды в обоих) + возврат. Разница хранилищ на фоне моста и сети
(1100 мс) неощутима. Дополнительно: новый завис, кастомные Tauri-команды,
ручная типизация, нет SQL/FTS, данные истории пришлось бы дублировать.

### Вариант B (отклонён): отдельная таблица/БД для кэша

Дублирование данных (история уже хранит text+source+target+service+result),
лишний файл/таблица без выигрыша.

### Вариант C (принят): L0 Map в памяти + L1 history.db с индексом

Двухуровневый кэш поверх существующей истории. Проверка — в начале
`translate()` в `TargetArea`, до сетевого вызова.

## 3. Решение

### L0 — Map в памяти окна перевода

- Ключ: `${text}|${source}|${target}|${instanceKey}` (instance key точнее, чем
  serviceName: разные инстансы ollama могут иметь разные модели/промпты).
- Попадание: ~мкс. Покрывает повторы в рамках сессии.
- Живёт в вебвью окна: сбрасывается при его пересоздании — не проблема,
  L1 восстанавливает.
- Значение хранить в исходном типе (строка или распарсенный объект словаря) —
  без повторного JSON.parse на каждое попадание.

### L1 — history.db

- Индекс при первом обращении:
  `CREATE INDEX IF NOT EXISTS idx_history_cache ON history(text, source, target, service)`.
- Запрос:
  `SELECT result FROM history WHERE text=? AND source=? AND target=? AND service=? ORDER BY id DESC LIMIT 1`
  (последний результат). Попадание: ~0,2–1 мс вместе с IPC.
- Ключ по serviceName — history хранит именно его; разные инстансы одного
  сервиса делят записи L1 (known limitation, для 99% случаев неактуально).
- Словарные результаты (объекты Google/ECDICT, `TargetArea:206`): при записи
  в history нестроковые значения уже сериализуются плагином; при чтении из
  кэша — `JSON.parse` если строка начинается с `{`, иначе вернуть как есть.

### Общий поток

```
translate(): L0 Map? → да → setResult мгновенно, стоп
              ↓ нет
             L1 history.db (индекс) → да → setResult, обновить L0, стоп
              ↓ нет
             обычный сетевой путь → успех → addToHistory (уже существует) + L0
```

### Конфиг

- Ключ `translate_cache` (по умолчанию `true`). Выключение = всегда ходить в
  сеть (на случай «нужен свежий перевод от сервиса»).

## 4. Обоснование

| Сценарий | Было | Станет |
|---|---|---|
| Повтор фразы в сессии | ~1,1 с (сеть) | ~мкс (L0) |
| Фраза, переведённая ранее (перезапуск) | ~1,1 с | ~0,2–1 мс (L1) |
| Новая фраза | ~1,1 с | без изменений |
| Офлайн, ранее переведённое | ошибка сервиса | результат из L1 |

Первичный путь не замедляется: до промаха добавляются только две локальные
проверки, суммарно << 1 мс на фоне 1100 мс сети.

## 5. Ограничения и риски

- **Устаревание результата**: сервис может со временем вернуть иной перевод —
  отдаём закэшированный. Принимаем (устойчивые выражения стабильны); обход —
  выключить `translate_cache`.
- **Рост history.db**: уже происходит; индекс добавляет ~размер индекса.
  Чистка истории — отдельная задача, не здесь.
- **Словарные форматы**: результат-объект хранится в TEXT-колонке —
  нормализация JSON.parse/stringify на границе кэша.
- **history_disable=true**: L1 пуст, работает только L0 — приемлемо.

## 6. Последствия и следующие шаги

1. Реализация: утилита кэша (src/utils/translate_cache.js) + вызовы в
   `TargetArea` до `translate()`; создание индекса — при первом `Database.load`.
2. Тесты: повтор фразы без сети (лог/отсутствие HTTP), перезапуск → L1,
   словарный сервис, `translate_cache=false` → сеть всегда.
3. Коммит в стиле `feat: ...`, без дополнительных подписей.
