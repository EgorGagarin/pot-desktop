# ADR 202611101859: Переезд на стек Rust (ядро) + Tauri (мост) + Svelte (интерфейс)

- **Статус:** принято
- **Дата:** 2026-11-10 18:59 (UTC+5)
- **Автор:** Egor Gagarin, исследование — ZCode-агент по коду форка, логам, апстриму pot-app/pot-desktop и внешним бенчмаркам
- **Контекст решения:** вопрос «даст ли переход на Rust + Tauri + Svelte выигрыш в скорости?» (перевод по хоткею должен появляться максимально быстро)

---

## 1. Контекст

Текущий стек pot-desktop 3.0.7 (форк EgorGagarin/pot-desktop):

- **Ядро — уже Rust** (2 423 строки): глобальные хоткеи, монитор буфера обмена, OCR (Windows.Media.OCR / Apple Vision / Tesseract CLI), детект языка (lingua), локальный HTTP-сервер (127.0.0.1:60828), скриншот, трей, конфиг (store-плагин).
- **Мост — Tauri 1.8** (WebView2 на Windows).
- **Интерфейс — React 18** + Vite 5 + NextUI + jotai + i18next: 17 920 строк JS, из них ~8 070 — сервисы перевода/распознавания/TTS (фреймворконезависимы), ~9 850 — UI.

Профиль бандла (замер `dist/`, сборка Nov 2026):

| Артефакт | Размер | gzip |
|---|---|---|
| JS (единый бандл на все окна) | 2,1 МБ | 584 КБ |
| CSS | 635 КБ | 110 КБ |

В бандл статически входят все ~40 сервисов, 21 локаль (363 КБ) и страницы настроек.

Наблюдаемая задержка «хоткей → перевод на экране» (тёплое открытие, Yandex):

| Этап | Оценка |
|---|---|
| Пересоздание окна перевода (`close_on_blur` → `appWindow.close()`) | ~0,3–1,7 с (первый webview в процессе), ~0,1–0,3 с (повторный) |
| Загрузка и парсинг бандла | ~0,2–0,4 с холодный, меньше тёплый (V8 code cache) |
| React mount + init (store, i18n, тема) | ~0,1–0,2 с |
| Получение выделенного текста (Rust) | ~0,05–0,1 с |
| Сеть (Yandex) | ~1,1 с — доминирует |

## 2. Рассмотренные варианты

### Вариант A (отклонён): полный переезд на Svelte 5

Svelte объективно быстрее React (krausest, Chrome 156, 2026): первая отрисовка 65 мс против 228 мс,
операции в ~1,5 раза быстрее, рантайм ~10 КБ против ~45 КБ brotli.
Лучший документированный кейс реального переезда — браузер Strawberry (130 тыс. строк):
FCP 300 мс → 124 мс, то есть **минус ~0,18 с**.

Оценка выигрыша для pot: **~0,1–0,25 с** на открытие окна (~10–15% тёплого пути),
потому что доминируют не фреймворк, а:

- создание WebView2-контрола: 0,3–1,7 с на первый webview в процессе
  ([MicrosoftEdge/WebView2Feedback #5796](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5796));
- сеть ~1,1 с — клиентски не ускоряется.

Стоимость: переписать ~9 850 строк UI, заменить NextUI, react-beautiful-dnd,
риск регрессий во всём интерфейсе. Плагины .potext переезд не ломает
(это eval-функции + generic-конфиг рендерит сам pot, React не трогают — проверено в `invoke_plugin.js:35`, `ConfigModal/index.jsx:17`).

### Вариант B (принят): точечные оптимизации текущего стека

Ранжировано по измеренному эффекту:

1. **hide() вместо close()** для окна перевода — минус ~1–2 с на каждый вызов.
   Апстрим измерил «свыше 2 секунд» на открытие и лечил именно этим
   ([PR #543](https://github.com/pot-app/pot-desktop/pull/543), ~100 МБ RAM за живое окно).
   Возражение мейнтейнера (настройки не обновляются в живом окне) решаемо: fs-watch
   уже следит за config.json — обновлять конфиг живого окна по событию изменения.
2. **Prewarm скрытого daemon-окна на старте** — сейчас оно создаётся лениво при первом
   переводе (`window.rs:17-35`), первый вызов после запуска платит полный холодный
   старт WebView2 (0,3–1,7 с).
3. **Кэшировать lingua-детектор (OnceCell)** — в форке `lang_detect.rs:57` пересобирает
   детектор на каждый вызов, а `init_lang_detect()` на старте строит детектор и
   выбрасывает результат (ничего не греет). Готовый код — в апстрим [PR #1290](https://github.com/pot-app/pot-desktop/pull/1290).
4. **Zero-polling буфера обмена** (AddClipboardFormatListener вместо 500-мс опроса) —
   минус ~250 мс средней задержки на перевод вставки. Тоже из PR #1290.

### Вариант C: Tauri 2

Отдельная миграция (плагины v1→v2 API). Ускоряет IPC в разы, но именно большие данные
(6,3 МБ: 48 мс → ~0 мс, mechanicalrock.io) — для абзацев текста выигрыш в шуме.
Оправдан ради поддержки (Tauri 1 не развивается), не ради скорости переводов.

## 3. Решение

Не переезжать на Svelte ради скорости. Выполнять вариант B по порядку (пункты 1–4,
каждый ощутим и независим). Svelte 5 возможен в будущем как проект осовременивания
кода, но не как средство ускорения перевода.

## 5. Последствия

- Положительные: 1–2 с на каждый вызов перевода после пункта 1; мгновенный первый
  перевод после старта (пункт 2); корректный и быстрый детект языка (пункт 3);
  мгновенный перевод вставки (пункт 4). Риск низкий — каждое изменение точечное.
- Отрицательные/ограничения: живое окно перевода держит ~100 МБ RAM (сделать
  опциональным конфиг-ключом); пункт 1 требует доработки синхронизации настроек;
  апстрим архивирован 07.09.2026 (read-only) — PR #1290 переносить в форк самостоятельно.
